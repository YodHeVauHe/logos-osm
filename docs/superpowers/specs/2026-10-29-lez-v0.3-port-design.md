# LEZ v0.3.1 OSM Registry Port Design

## Intent

Port the LP-0018 registry from the legacy `ProgramInput` / `ProgramOutput` execution model to the plan/apply guest model shipped in LEZ tag `v0.3.1`. Keep registry semantics and the host SDK API stable where practical, and make transactions and reads target a configurable v0.3.1 sequencer.

## Goals and constraints

- Pin `lee_core` to the LEZ git tag `v0.3.1`; use the RISC Zero versions selected by that tag (including `risc0-zkvm = 3.0.5`).
- Preserve permissionless idempotent init, entry validation and positive timestamp checks, upsert semantics, batch limit, Borsh registry representation, byte ceiling, error codes, and cycle log labels.
- Guest instructions use Borsh enums. Inputs carry the registry account meta and instruction payload; effects carry validated changes into apply.
- No testnet deployment or keys in the repository. Local integration uses a throwaway wallet home under `/tmp`.
- Build through the installed RISC Zero toolchain without Docker if `cargo risczero build` can use it; clearly report reproducibility limits.

## State layout

The complete `osm_registry_core::Registry` stays encoded as Borsh bytes in a public shard whose owner is the deployed registry program account. Its account ID is `AccountId::for_public_pda(program_account_id, PdaSeed::new(seed))`, where the 32-byte seed is the ASCII string `registry` followed by zero bytes. Calls pass the registry account selector and a signer selector. This chooses the program's own shard so the guest can write it, while the deterministic public PDA lets clients read its shard from account data. The encoded state remains capped at `MAX_ACCOUNT_BYTES`.

## Instructions and behavior

The guest has `InitRegistry`, `RegisterRegion(RegionEntry)`, and `RegisterBatch { entries: Vec<RegionEntry> }` Borsh variants. `registered_by` stays in each `RegionEntry` (and the SDK fills it consistently for batches); no redundant string or hex payload is needed in the on-chain instruction. The plan validates instruction shape, account count/ownership, entries, batch size, registry bytes and timestamps, then emits a single registry shard effect. Apply rechecks the effect's encoded transition against current shard bytes, so invalid state changes cannot enter from an untrusted plan output. Init of empty state writes the default registry; init of an existing registry preserves it.

## CLI and SDK

The registry CLI is a direct v0.3.1 wallet/RPC client: it accepts sequencer URL and wallet home, builds public transactions using the wallet core and LEZ RPC client, and reads registry data from the public account shard. SDK `RegistryClient` remains stable; its implementation invokes that CLI for writes and queries the sequencer account endpoint for reads (not legacy `lgs` or SPEL). Account IDs and instruction serialization follow the LEZ v0.3.1 API.

## Build, IDL, and deployment

The guest is compiled as a RISC Zero guest against the tagged LEZ dependency. The resulting ELF is wrapped only if the v0.3.1 `wallet program-loader` format requires it; the build prints the image ID / ProgramId. IDL documents Borsh instruction variants, the registry PDA and signer meta, and public shard reads. LEZ references in manifests, examples, tools, scaffold metadata, and docs point at `v0.3.1`.

## Testing and verification

Pure plan/apply logic is host-testable and gets unit tests first, including init idempotency, upserts, validation errors, timestamp rejection, batch limits, size limits, and malformed state/effect handling. The local e2e launches the v0.3.1 sequencer and uses its wallet/RPC path with a temporary home, then confirms on-chain shard decoding. Existing workspace and e2e tests, formatting, clippy, IDL reproducibility, submission-doc checks, and Nix availability are reported from actual runs. The CI chain job uses the LEZ v0.3.1 sequencer and wallet.

## Approaches considered

1. **Direct plan/apply guest (selected):** use `lee_core` APIs and wallet/RPC patterns from v0.3.1. This matches the required live network model and removes SPEL from active build paths.
2. Keep SPEL and add a compatibility shim: rejected because upstream SPEL targets v0.2.5-rc2 and its input/output ABI does not express v0.3.1 plan/apply.
3. Keep the old guest and only adapt clients: rejected because the deployed v0.3.1 sequencer cannot execute that guest ABI.

## Not goals

This work does not deploy to testnet, claim LP-0018's required LEZ 0.4 deployment, change prize text, create wallet keys in the repository, or remove historical SPEL documentation/vendor history unless active build references require it.
